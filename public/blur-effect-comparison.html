▣ Architecture Layers

Web CSS — Layer Stack

1 .topbar (z-index: 2) Header bar — position: relative
2 .topbarBlur::after Gradient mask (solid → transparent)
3 .topbarBlur::before backdrop-filter blur (frosted glass)
4 .content (scrollable) Scrolling content underneath

Android — Layer Stack

1 TopAppBar composable Header — clips to rounded shape
2 Box(Modifier.graphicsLayer) RenderEffect blur + opacity
3 Canvas.drawWithContent Alpha gradient mask overlay
4 LazyColumn / RecyclerView Scrolling content underneath
5 DataStore preference ON/OFF toggle persistence

◉ Web CSS — Pros & Cons

Advantages

  • Zero JavaScript for rendering — the entire visual effect is pure CSS. Only a tiny rAF scroll listener sets one CSS variable. The browser's compositor handles everything else at 60fps.
  • Instantly portable — the same CSS works on iOS Safari, Android Chrome, Firefox, Desktop. No per-platform code needed. One implementation serves all devices.
  • GPU-composited — backdrop-filter runs on the GPU compositor thread, never blocking the main thread. will-change: opacity hints layer promotion.
  • Trivially configurable — CSS custom properties (--blur-corner-radius, --blur-filter-radius, --blur-fade-height) let you tune every parameter per-element or globally with zero code changes.
  • Built-in fallback — @supports not (backdrop-filter) gracefully degrades to gradient-only. No feature detection code, no runtime checks.
  • Border-radius clipping is free — CSS automatically clips both ::before and ::after to the parent's border-radius. No manual clip math needed.
  • Easy to prototype and iterate — change one CSS value, see the result instantly. No rebuild, no redeploy, no emulator.

Disadvantages

  • Browser support gaps — Firefox only added backdrop-filter in v103 (2022). Older browsers and some WebViews don't support it at all — the fallback is gradient-only (no actual blur).
  • No control over blur algorithm — the browser decides the blur quality and radius interpretation. You can't choose box vs gaussian vs stack blur. Different browsers may render slightly differently.
  • No per-screen toggle — currently the prototype has no Settings toggle to enable/disable the effect. Every screen always has it (when scrolled). Adding a toggle requires JavaScript to gate the CSS variable.
  • Pseudo-element limit — using ::before and ::after means the element can't use pseudo-elements for anything else (e.g., decorators, tooltips). In practice this is fine for a dedicated blur element.
  • Static export constraint — because this is a Next.js static export deployed to GitHub Pages, there's no server-side rendering or dynamic API. Everything must be client-side.
  • Color-mix() browser support — the gradient stops use color-mix(in srgb, ...) which requires Chrome 111+, Safari 16.2+, Firefox 113+. Older browsers get broken gradient stops.

◉ Android Native — Pros & Cons

Advantages

  • Native GPU blur — RenderEffect.createBlurEffect() is a true hardware-accelerated Gaussian blur running on the GPU render thread. Consistent quality across all devices that support it.
  • Full control — you choose the blur radius (float), the input and output ContentInfo, and can chain multiple effects (blur + color filter + offset). Not limited to what CSS exposes.
  • Seamless Settings toggle — DataStore persistence with a Compose Switch in Appearance → General. The toggle gates the entire blur composable. No CSS variable hacks needed.
  • Compose declarative model — the blur is a composable function with parameters. You call BlurHeader(fadeHeight = 32.dp, cornerRadius = 24.dp) and it just works. Reusable across all 6 screens.
  • Player screen integration — can place the blur below the player controls overlay (exo player), blurring the content scrolling behind the player. CSS can't do this in the web prototype because the prototype doesn't have a real player.
  • Gradual fallback strategy — API 31+ gets full RenderEffect blur. API 21–30 gets a gradient-only overlay (Brush.verticalGradient). Users on older phones still get a decent effect.
  • Branch-based workflow — development happens on a feature branch, verified via GitHub Actions APK build, merged only with user approval. Production-safe.

Disadvantages

  • API 31+ required for real blur — RenderEffect only exists on Android 12+. On API 21–30 (roughly 30% of active devices), users only get the gradient fallback — no actual frosted glass.
  • Performance concern on low-end — real-time RenderEffect blur on a scrolling LazyColumn can be expensive on budget devices (Mali-G52, Adreno 505). May need to throttle blur updates or reduce radius on low-RAM devices.
  • More code — the Android implementation requires: a reusable composable, scroll offset observation, graphicsLayer modifier, RenderEffect setup, gradient brush drawing, DataStore preference, Settings UI toggle. Roughly 200–400 lines of Kotlin vs 60 lines of CSS.
  • No real-time preview — changing blur parameters requires a full app rebuild + deploy (even with Compose Preview, blur effects don't render in @Preview). Slower iteration than CSS.
  • Detail screen complexity — the detail page has a collapsing toolbar + backdrop image + blur header. Integrating blur with CollapsingToolbarLayout or custom scroll behavior adds significant complexity.
  • Memory overhead — RenderEffect allocates hardware bitmaps for the blur input. On a 390×32px area this is negligible, but it's still more memory than CSS (which reuses the browser's existing compositor textures).
  • Testing burden — need to verify on multiple API levels (21, 23, 26, 31, 33+), multiple screen sizes, and multiple GPU vendors. GitHub Actions can only verify compilation, not visual correctness.

Summary & Recommendation

The Web CSS approach is ideal for the current prototype — it's minimal code, instantly iterative, and works across all modern browsers. The Android Native approach is the right choice for production — it gives full control, native performance, and proper Settings integration. They solve the same visual problem with fundamentally different tools, but the end result (frosted glass with curved corners fading smoothly on scroll) should look and feel nearly identical.

Both implementations share the same core design principles: two-layer architecture (blur + gradient mask), smoothstep easing for opacity, rounded bottom corners for the curved device feel, and a graceful fallback when blur isn't available. The web version proves the visual design; the Android version makes it production-ready.

⚡ Key insight: The web prototype serves as the visual reference and design proof. The Android implementation translates the same visual spec into native code. Keep both in sync — if you change the blur radius or corner curve on the web, update the Android defaults to match.
